# Challenge-v1：更有区分度的仓颉修复实验

执行更新（2026-11-26）：已完成独立 6 题开发校准，A 首轮 4/6，达到预设区间，保留原评估设计。下文为生成前的登记文本。[校准记录](experiments/2026-11-26-challenge/calibration.md)

登记日期：2026-11-26。当前交付是新题、测试、材料验收和离线请求设计，**没有新一轮模型成绩，难度尚未校准**。原首轮 A/B 的 A 16/16、B 16/16 保留，见[首轮报告](experiments/2026-11-26-pilot/report.md)。不能因上一轮满分就删掉结果，也不能通过挑选“只有 B 会做”的题来证明检索有效。

## 1. 要回答的问题

在同一仓颉版本、同一模型和同一修复机会下，按当前问题检索官方文档，是否比不给文档更容易修好程序？如果有提升，是否也优于每题都给相同的文档速查表？

困难来自两处独立错误、跨方法状态变化、引用副作用和算法边界；不是单纯把程序写长。完整成功指编译、公开行为和保留行为均通过，只编译成功不算修好。

## 2. 检索到的 benchmark 与取舍

| 来源 | 适合借鉴什么 | 本项目怎样使用、不能声称什么 |
| --- | --- | --- |
| [CangjieBench](https://github.com/cjhCoder7/CangjieBench)，[论文](https://arxiv.org/abs/2603.14501) | 164 个 HumanEval、84 个 ClassEval 仓颉任务；类级方法和状态比单行类型题更复杂 | 固定上游提交，适配 10 个 ClassEval 参考实现，另植入双故障和新测试。原任务是生成/翻译，不能把本次修复率称为原榜单成绩。 |
| [QuixBugs](https://github.com/jkoppel/QuixBugs) | 40 个经典算法缺陷；边界与控制流错误 | 参考任务族，新写 10 个仓颉程序与 JS 测试 oracle、加入双故障；不是对原 Java/Python 单行错误的直接复现。 |
| [DebugBench](https://github.com/thunlp/DebugBench) | 多种缺陷类别、难度分层 | 借鉴分层思想，没有复制其题目代码；不用题长冒充难度。 |
| [EvalPlus](https://github.com/evalplus/evalplus) | 更强的测试能识别只过示例的错误实现 | 增加边界、连续调用、别名副作用和单故障检出检查；测试充分性仍有限。 |
| [SWE-bench](https://github.com/swe-bench/SWE-bench) | 真实仓库 issue、跨文件修改及回归 | 当前工具是受限单文件仓颉修复，不直接引入大型仓库任务，也不据此声称优于 Agent。 |

代码来源、固定提交、MIT 许可和逐题适配见[来源表](../data/experiments/challenge-v1/benchmark-sources.md)。公开 benchmark 可能被模型训练见过；新增故障和测试不能证明“零污染”。任务、参考、测试由 Codex 辅助构造和检查，尚无独立成员复核或学生试用。

## 3. 题目与测试

| 分层 | 评估题 | 独立开发题 | 例子 |
| --- | ---: | ---: | --- |
| 语言/API 与语义 | 8 | 2 | Unicode 码点旋转、Option、集合接口、数组引用副作用 |
| 算法与边界 | 8 | 2 | 0/1 背包、编辑距离、最短路、重复元素的下一个排列 |
| 类与状态 | 8 | 2 | 预约与入住、跨次经验累计、库存、分页、账户转账 |
| 合计 | **24** | **6** | 同一题族不跨开发/评估分割 |

每题两处植入错误，同时保留两个“只剩一处错误”的版本。当前 30 题共有 **196 条保留断言、60 个单故障版本**。一条断言可联合检查多个条件；断言数不是独立样本数，更不是覆盖率。公开测试给模型看；保留测试不进入提示、检索库或第二轮反馈。

材料必须先在 SDK 1.0.5 的 Linux 受限容器通过以下检查：

1. 参考实现通过公开测试和保留测试。
2. 双故障原程序至少一项公开检查失败。
3. 两个单故障版本分别失败，防止只改其中一处也算成功。
4. 没有工具异常、未确认清理的容器；工具错误不能当作检出了程序错误。

每题 5 次验证，共 150 次。API 故障可能在编译时被检出，逻辑故障通过运行断言检出，必须分别报告，不能把编译失败都包装成保留测试覆盖。此门槛仅证明这些已知错误被检出，不能证明所有错误实现都会被排除。

首轮材料验收 [45785574677](https://github.com/Frank72316/cangjie-code-doctor/actions/runs/45785574677) 为 29/30：RPG 测试把元组下标误写为 `.0`，参考程序因此无法编译；已按同版本文档改为 `[0]`。后续复核又补强该题连续未升级时的累计测试，防止覆盖经验的单故障漏过。完整复测另行留存，没有模型生成结果参与这些修正，原失败记录保留。

最终[材料验收45788677064](https://github.com/Frank72316/cangjie-code-doctor/actions/runs/45788677064)已通过全部30题门槛；60个单故障中54个运行失败、6个编译失败。150份报告与冻结源码/测试摘要逐一核对，见[准备报告及回执](experiments/2026-11-26-challenge/report.md)。这不改变“模型难度尚未校准”的状态。

## 4. 三组对照与固定输入

| 组别 | 模型获得的信息 | 用途 |
| --- | --- | --- |
| A | 题意、错误源码、公开测试、原始编译/运行反馈 | 无文档基线 |
| B | A 的全部内容 + BM25 检索前 3 个片段 | 主要考察按问题选文档的效果 |
| C | A 的全部内容 + 每题相同的 3 个官方片段 | 固定速查表基线，判断是否需要按题检索 |

主要比较 B−A，次要比较 B−C。C 固定为 ArrayList、Option、函数调用三个章节的首个片段，不针对某题换文档。B 和 C 均最多 3 段、每段不超过 1600 字符，**实际长度不严格相等**；报告真实输入 tokens 和费用，不声称完全控制了上下文长度。这个 C 也不能代表所有可能的最佳速查表。

新检索库独立于旧 pilot：从官方 SDK 1.0.5 固定提交的 19 个完整通用章节确定性切分成 63 段，共 150700 字节。构建器不读取题目或答案，保留逐段原文、来源、行号、许可和哈希；章节选择由研究者制定，仍可能存在选择偏差。旧网页与 pilot 文档快照不改。

B 使用项目原生仓颉 BM25，k1=1.2、b=0.75、topK=3；查询由初始诊断、源码标识符和题意确定性形成，不读取人工标注的故障位置、docTopics、参考实现或保留测试。检索无命中就如实记录，不人工替换片段。两轮均使用同一份初始检索，避免同时改变查询迭代策略。

准备脚本会记录“是否命中相关章节”，这只是使用预先登记主题做的粗略章节核对，**不等于片段真的回答了修复问题，也不是模型成绩**。正式分析另行阅读片段，区分无关、只有背景和直接相关，不根据评分结果修改已冻结检索。

模型拟用 deepseek-flash，关闭思考、temperature=0、top_p=1、max_tokens=4096，JSON 输出，不使用模型工具。A/B/C 的系统提示与公共任务完全一致，只改变 documents 字段。模型别名可能随服务更新，保存返回模型标识、时间和实际参数；温度为 0 也不保证每次完全相同。

## 5. 先校准，再冻结评估

开发集只有 6 题，不入正式成功率分母。先做 A/B/C 各一次，观察参考门槛、输出截断、提示可理解性及 A 首轮通过数。预定的粗略开发诊断：A 通过 2–4/6 时可以继续；0–1/6 提示可能过难，5–6/6 提示仍有天花板。样本很小，这只是工程检查阈值，不是统计证明。

最多根据开发集做一次有版本记录的统一修订，再重新验收和冻结；不能查看正式评估 A/B 差异后挑题、换保留测试或增加轮数。开发集第二次仍出现天花板/地板就报告局限，不反复调到 B 获胜。正式评估结果只能用于分析和未来另一个版本的设计。

本次没有付费校准调用，故 `difficultyCalibrated=false`、`readyForFormalModelRun=false`。当前离线请求文件是设计预览，不能冒充正式冻结或真实成绩。

## 6. 正式执行计划（尚待接入运行器）

24 题 × 3 组 × 3 次独立重复 = **216 个条件任务**。每个任务最多两轮，最多 **432 次模型调用**。开发集另计 18 个条件任务，最多 36 次。顺序按分层交错、六种 A/B/C 顺序轮换，第二、三次重复再轮换；保存明确顺序，避免所有 A 先跑、B 后跑造成系统性时间偏差。

首轮只看公开反馈。公开检查全过就停止；失败则把该条件自己的候选及公开反馈交回同一模型再改一次，不看其他组输出，不泄露保留信息。采用最后一份格式有效的候选；若第二轮返回无效格式，保留首轮候选并记录失败。不得由人替模型改代码。超时、API 错误和预算中止均留记录，无自动收费重试；报告完整性，不能把缺失配对删掉后称完整实验。

所有正式候选锁定后才解密保留测试评分。检查函数签名/题意行为是否被保留，并复核硬编码、删除函数、替换测试等投机行为；违规单列且不计成功。二轮生成、公开验证调度、预算锁定与最终评分接线尚未完成，不能直接用旧单轮 pilot 运行器冒充新协议。

沿用现有 GitHub Linux 隔离环境：固定 SDK 和镜像身份、无网络、资源上限、源码只读挂载、清理可核对。API Key 只留本机，候选和公开证据可上传；保留材料只上传密文、解密钥匙独立。无模型调用的材料检查与离线 BM25 不消耗模型余额。

费用控制以既有 20 元授权作为累计上限，扣除首轮实验保守估算 0.098134 元后至多剩 19.901866 元用于后续实验估算；这不是实扣账单或新的 20 元额度。付费前须核对当时官方价格，按最大输出和剩余输入预算预留每次费用，不能仅看已消耗后继续超额。开发调用等已知开销也应在实际账本中计入。**本次不触发任何新付费请求。**

## 7. 怎样报告结果

- 主指标：每题三次重复的完整成功比例，按 24 题等权平均，比较 B−A；另报 B−C、三类各 8 题和每一轮表现。72 次尝试不是 72 个独立题，不能据此夸大样本量。
- 报告首轮与最多两轮的成功数、公开过但保留失败、编译失败、格式/API/执行异常和违规候选；第二轮的增益单列。
- 同时报输入/输出 tokens、调用数、延迟、估算费用和每个新增成功所需成本。B 成本更高却没有更多成功，也是一条有意义的结论。
- 如给出不确定性区间，按题成簇重采样，整组保留 A/B/C 和三次重复；24 题、每层 8 题只支持探索性分析，不包装成普遍因果结论。
- B 与 A 都高：讨论天花板和选题；都低：讨论难度或工具限制；B 不如 A：分析无关检索/误导片段；B 与 C 接近：不能把一般文档帮助归功于检索算法。没有预设 B 必须胜出。
- 即使修复率更高，也只适用于本案例集、版本、模型和预算；本实验没有比较自主 Agent，也没有测量学生学习效果。

## 8. 文件与复现

公开题与语料：`data/experiments/challenge-v1/`。参考、单故障和测试构造脚本封存在该目录的 `holdout.enc.json`；本机解密钥匙和明文在被忽略的 `data/holdout/challenge-v1/`，不能提交。

1. `scripts/verify-challenge-materials.mjs`：仅 Linux 不可变镜像，产出材料回执、初始公开反馈与加密完整证据；由 `challenge-materials.yml` 调度。
2. `node --test tests/challenge-data.test.mjs tests/challenge-design.test.mjs`：清单、摘要、分割、条件顺序和提示差异检查。
3. SDK 环境就绪后运行 `node scripts/prepare-challenge-design.mjs <initial-feedback.json> <receipt.json> <不存在的输出目录>`。脚本拒绝不通过或哈希不一致的材料回执，调用原生 BM25，保存 A/B/C 首轮请求与哈希、顺序表；没有联网模型调用代码。
4. 本机保留钥匙就绪后，可运行 `node scripts/check-challenge-material-evidence.mjs <材料归档目录>`，解密并核对全部150份报告的源码、测试请求摘要、材料门槛和容器清理状态。该操作不运行候选、不调用模型。
