# 中期答辩讲稿与追问准备

适用日期：2026-11-16。组长：张宇宸。以下为汇报提纲，不是正式实验结果。

## 建议的五页内容（约五分钟）

1. **问题与定位（40秒）**：我们研究仓颉程序诊断和修改验证，计划回答“加入同版本官方文档检索，修复成功率有没有变化”。第3组面向知识点和练习的学习闭环；本组侧重受控修复流程与证据。两者可合作，不以功能互斥划边界。
2. **系统与已完成内容（60秒）**：展示定位、文档依据、人工确认、测试验证和报告的流程。说明仓颉核心承担诊断解析、检索和公开输出判定，网页负责交互，Node服务负责传输与容器调度。用户副本与原始记录分离。
3. **真实成功路径（60秒）**：展示类型不匹配的原报错，将字符串改为整数3，附同版本文档，再展示Linux容器公开测试通过。说明这是人工预设的开发案例，界面在Windows回看，并非本机即时运行。
4. **失败路径与证据（60秒）**：改为整数4仍可编译，但公开期望仍是3，系统明确显示输出不符。报告绑定源码、测试与原始输出，单独改动内容会被拒绝。哈希不是数字签名，也不能证明所有输入都正确。
5. **后续计划与边界（60秒）**：先扩充和复核案例，再确定模型、预算及参数，完成候选流程、保留测试独立判定和冻结，最后做配对A/B及学生试用。未观察到检索优势也如实报告，工具可用性另行验收。

## 老师可能追问

**为什么先没接AI？** 当前先验证诊断、保存、隔离执行与证据留存链路，避免模型接入后无法区分建议错误和工具故障。模型接入仍是后续必做，不以界面替代功能。

**实验如何保证公平？** 同模型同参数同案例，A不检索，B加入同版本文档；两轮预算一致，保留测试不反馈给生成过程，候选锁定后独立评估。具体以冻结后的协议为准，当前尚未完成冻结。

**两组结果一样怎么办？** 报告本案例集的配对原始计数、差值、失败和成本。未观察到优势不等于证明普遍无效；若B较差也保留结果，不临时换分母或删除负面案例。

**这能说明程序完全正确吗？** 不能。公开测试只覆盖指定输入，正式修复成功还要满足预定保留测试规则；即使测试都通过，仍需说明有限覆盖与语义审查边界。

**如何证明不是临时编造？** 展示提交记录、对应CI平台时间、原采集清单、成功和失败原始报告。Git提交时间与平台创建时间分别记录，不用文件修改时间冒充上传时间。
