# 哪段 API 文档有助于修复仓颉程序？

上一轮 24 题的三组最终通过率接近，Unicode 轮转却在所有组失败。此次把同一问题拆成文档内容和自动选段两个因素。此前已知旧题成绩。这是一轮有针对性的后续研究。

## 实验单位与比较

固定取上一轮全部 8 道正式语言/API 题，加 4 道新编字符串题，分别覆盖隔位取码点、只删一次后缀、限制分割段数和按字符集修剪尾部。新题与旧题分别统计。四道新题的公开样例与保留测试先锁定，由 Linux SDK 1.0.5 检查原始程序、参考实现和两套测试。没有根据新题模型结果挑题。新题属于定向的标准库迁移任务，不能代表所有学生错误。

每题四组、每组三次、每次只看到首轮公开题面与初始错误反馈，共 144 次独立请求。共用原生仓颉 BM25 排出的前两段开发指南，仅改变模型看到的第三段：

|组|第三段|
|---|---|
|R 原检索|开发指南的原始第 3 名|
|M 自动 API|固定的 SDK 1.0.5 标准库索引中，原题相同查询的 BM25 第 1 名|
|G 指定 API|按题意预先指定的一个官方 API 条目|
|P 无关 API|在同一索引的 Duration 条目中，选择正文 UTF-8 字节数最接近 G 的一段，并按 ID 破同分|

指定的条目是研究者对可用文档的一种选择，不排除其他正确写法。M 的查询不读取指定条目、参考解或保留测试。主比较为 G−P（具体内容是否改变成功率），次比较为 M−R（自动替换第三段是否有改善）和 G−M（自动选段留下多少差距）。另报 M 在第 1 名、前 3 名包含指定条目的题数。这是精确条目命中率，低分时需人工查看替代条目的意义。G 和 P 长度近似，报告实际输入 tokens。服务端对响应的缓存和时间漂移均可能存在。

题目按新旧交错，四种组序采用平衡拉丁方，每次重复轮换。统计以题为配对单位，三次平均后按题等权。报告原始分子、逐题方向及按新旧题分别有放回重采样 10000 次的探索性区间（种子 20261126）。不挑最好的重复，不按结果追加重试或剔除平局。若新旧差异明显，分别解释。不把本轮复测和上一轮合并为独立样本。

## 模型、验收与预算

使用 DeepSeek Flash、关闭思考、温度 0、top_p 1、最多 4096 输出 tokens。所有组系统提示、修复任务和反馈相同，仅 documents 的最后一段变化。一次生成，无反馈重试。在本机生成并锁定全部候选后再做候选评分。判定依次检查可解析回复、可信原题入口编译与公开行为、冻结保留行为，最后审阅成功源码有无替换题意或硬编码。沙箱基础设施失败要另外处理，不算成模型错误。原题与保留入口分开执行。原始证据加密存档；模型看不到保留输入、参考实现或其他组回答。
